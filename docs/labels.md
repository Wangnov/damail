# 标签和 AI 标签推荐

状态：**已实现**（第一版）。第二版（多语言、分类和提示词入库）见文末，也已实现。

## 要解决的问题

AI 分类是固定的 10 个（`server/src/services/ai.ts` 的 `CATEGORIES`），用户没法按自己的需要细分，比如“券商交易通知”“云服务账单”“某个项目”。
让用户自己写分类名和说明也不好：说明写得含糊，AI 就会分错，用户还不知道为什么。

做法：在分类之外加一层**标签**，主要入口是 **AI 根据用户以往的邮件推荐标签**，名称和判断说明都由 AI 根据真实邮件来写，用户只决定要不要。

## 分类和标签的区别

| | 分类（不变） | 标签（新增） |
|---|---|---|
| 每封邮件 | 恰好一个 | 零个或多个 |
| 数量 | 固定 10 个 | 用户自己的，上限 50 个 |
| 来源 | AI 分析时选 | AI 推荐后用户采用，或用户手动建；新邮件由 AI 按说明自动打 |
| 用途 | 优先级、概览、日报、规则 | 细分、侧栏快捷入口、搜索、规则 |

分类相关的代码一律不动。

## 用户流程

1. 进入「AI → 标签」页，点「根据我的邮件推荐标签」。
2. 后台跑一个任务（几十秒），页面显示进度；完成后列出建议，每条有：
   - 名称、颜色；
   - AI 写的判断说明（包括什么、不包括什么）；
   - 覆盖的历史邮件数，和 3～5 封例子（点开看原邮件）。
3. 每条可以「采用」「忽略」，采用前可以改名称、颜色，说明也能改但默认不用动。
4. 采用后：
   - 推荐时覆盖到的历史邮件**直接打上标签**（不再调用 AI）；
   - 之后的新邮件在 AI 分析时按说明自动判断要不要打。
5. 以后可以随时再点一次推荐：只推荐现有标签还没覆盖的类型，忽略过的不再推荐。

用户也可以手动新建标签（填名称和说明），作为补充入口，不放在主要位置。

## 推荐怎么算

目标：几百上千封邮件只调用一两次 AI，而且推荐基于真实邮件。

### 1. 不用 AI 先分组（只查数据库）

- 范围：最近 90 天，所有启用的邮箱，不含已删除、垃圾邮件文件夹、忽略名单里的发件人、AI 判为 `spam` 的。开发库实测约 730 封、210 个发件人。
- 按发件人地址分组（小写）；同一域名下有多个发件人地址的，再合成一个域名组，组里保留各地址的封数。
- 每组带上：发件人名字、地址或域名、封数、现有 AI 分类的分布、最近 5 封的主题和 AI 摘要（没分析过的只有主题）。
- 去掉少于 3 封的组；按封数排序，最多取 120 组（控制提示词在约 2 万 token 内）。
- 已经被现有标签覆盖大部分（超过 80%）的组不送去推荐。

### 2. AI 归纳成标签建议（一次调用，邮件很多时分两批）

提示词要点：

- 输入：上面的分组概况、用户已有的标签（名称和说明）、用户忽略过的推荐名称。
- 要求：
  - 推荐 3～12 个对用户**有用的细分**；不推荐和内置分类重复的大类（如“账单”“验证码”），也不推荐只有一个发件人且没有实际意义的标签；
  - 可以把多个组合成一个标签（如多家券商合成“券商交易通知”），也可以只取组的一部分（说明里写清楚条件）；
  - 说明写成**判断规则**：包括什么、不包括什么，一两句话，不写“这类邮件很重要”之类的评价；
  - 名称简短（2～8 个字）、语言跟随界面语言。
- 输出（结构化）：

```json
{"suggestions": [{
  "name": "券商交易通知",
  "description": "Interactive Brokers、富途等券商发的成交确认、持仓日报、入金到账通知；不包括券商营销邮件和验证码",
  "groups": ["g3", "g17"],
  "reason": "两家券商共 37 封，每周都有"
}]}
```

- 和分析邮件一样，邮件内容是不可信数据，提示词里声明只分析不执行。

### 3. 算出覆盖的邮件

建议里的 `groups` 对应的邮件就是“覆盖的历史邮件”，存下这些邮件 id，例子从里面取最新的 5 封。
不逐封再问 AI：同一发件人的邮件归属已经比较稳定；少数不该打的，用户可以在邮件里手动去掉。

## 新邮件怎么自动打标签

**并进现有的分析调用**（`classifyMessage`），不另外调用 AI：

- 系统提示后面追加一段标签列表（用户没有标签时不追加，提示词和现在完全一样）：

```
标签（可以多选，也可以一个都不选；只有明确符合说明时才打）：
- L3 券商交易通知：Interactive Brokers、富途等券商发的成交确认……
- L7 云服务账单：……
```

- 输出 schema 增加 `labels: string[]`（值是 `L<id>`）。Anthropic 用结构化输出时按当前标签动态生成枚举；OpenAI 兼容接口按宽松格式解析，丢掉不认识的值。
- 提示缓存：固定的分类提示放在第一段并带 cache_control，标签列表放第二段也带 cache_control。标签不改时两段都能命中缓存。
- 标签说明会进提示词，长度限制 200 字；名称 20 字。

**手动修改优先**：

- 用户手动加的标签，重新分析不会去掉；
- 用户手动去掉的标签，留一条“已去掉”的记录，重新分析不会再打回来。

**新建或采用标签后，以前的邮件**：

- 推荐采用的：直接用推荐时算好的邮件（见上）。
- 手动新建的：标签页提供「给最近 N 天的邮件补打」，复用现有的重新分析任务（会消耗 AI 额度，页面上写清楚封数），只对还没有这个标签的邮件跑。

## 数据表

迁移 `0022_labels.sql`，只新增表，不改现有表：

```
labels
  id            serial PK
  name          text NOT NULL            -- 唯一（不区分大小写）
  description   text NOT NULL            -- 给 AI 的判断规则
  color         text NOT NULL
  pinned        boolean NOT NULL DEFAULT true   -- 显示在侧栏
  source        text NOT NULL            -- suggested | manual
  created_at, updated_at

message_labels
  message_id    bigint  → messages.id ON DELETE CASCADE
  label_id      int     → labels.id   ON DELETE CASCADE
  source        text NOT NULL            -- ai | manual | suggestion
  removed       boolean NOT NULL DEFAULT false   -- 用户手动去掉的记录，列表和搜索里不算
  created_at
  PRIMARY KEY (message_id, label_id)
  INDEX (label_id, message_id) WHERE NOT removed

label_suggestions
  id            serial PK
  run_id        uuid NOT NULL            -- 同一次推荐
  name, description, color, reason
  message_ids   bigint[] NOT NULL        -- 覆盖的历史邮件
  status        text NOT NULL            -- pending | accepted | dismissed
  label_id      int NULL → labels.id ON DELETE SET NULL   -- 采用后对应的标签
  created_at
```

- 新一次推荐开始时，上一次还是 pending 的建议标成过期（不删除，dismissed 的名字留着给 AI 参考）。
- 多用户分支（`multi-user`）恢复开发时，`labels`、`label_suggestions` 要加 `user_id`，记进该分支的 `docs/multi-user.md`。

## 接口

都在 `/api/admin`（网页会话）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/labels` | 标签列表，带邮件数、未读数 |
| POST | `/labels` | 手动新建 |
| PATCH | `/labels/:id` | 改名称、说明、颜色、是否显示在侧栏 |
| DELETE | `/labels/:id` | 删除；引用它的规则会提示 |
| POST | `/labels/:id/backfill` | 给最近 N 天的邮件补打（走重新分析） |
| POST | `/label-suggestions/run` | 开始一次推荐，返回任务 id；同时只能有一个在跑 |
| GET | `/label-suggestions` | 当前推荐和任务状态 |
| POST | `/label-suggestions/:id/accept` | 采用（可带改过的名称、颜色、说明） |
| POST | `/label-suggestions/:id/dismiss` | 忽略 |

开放接口 `/api/v1` 和 MCP：

- 邮件、会话返回的数据里带 `labels: [{id, name, color}]`；
- `PUT /api/v1/messages/:id/labels`（organize 权限）：手动加、去掉；
- 搜索语法支持 `label:名称`，MCP 说明里列出用户的标签名。

## 用到标签的地方

- **邮件列表**：分类标签后面显示邮件的标签（最多 2 个，多的用 +N）。
- **邮件详情**：显示全部标签，可以加、去掉。
- **侧栏**：「分类」下面加一组「标签」，只列开了“侧栏显示”的，带未读数；点进去就是 `label:名称` 的搜索，「全部 / 未读」筛选照常可用。
- **搜索**：`label:券商交易通知`，中文写法 `标签:券商交易通知`。
- **规则**：条件里加“有标签 …”，比如打了“券商交易通知”就推送到某个渠道。规则在 AI 分析之后执行，所以能用上新打的标签。
- 概览、日报、统计这次不改。

## 边界情况

- AI 没启用：推荐按钮不可用并提示先配置模型；手动建标签、手动打标签照常可用，只是新邮件不会自动打。
- 推荐时邮件太少（分组后不到 3 组）：直接提示“邮件还不够多，过段时间再试”，不调用 AI。
- 标签名重复：采用推荐时如果和已有标签重名，提示改名或合并到已有标签（合并时把覆盖的邮件打上已有标签）。
- 删除标签：邮件上的标签一起删除；引用它的规则不会静默失效，规则页把这条规则标成“条件引用的标签已删除”，并且不再匹配。
- 忽略名单里的发件人：不送给 AI，推荐和自动打标签都跳过。
- 标签上限 50 个：超过时推荐只给出“合并或删除不用的标签”的提示，不再推荐新的。

## 成本

- 一次推荐：1～2 次调用，输入约 1～2 万 token。
- 每封新邮件：提示词多一段标签列表，每个标签约 60 token，10 个标签约 600 token，而且能命中提示缓存。
- 推荐采用后给历史邮件打标签：不调用 AI。

## 测试

后端（`server/test/labels.test.ts`，用假的 AI 返回，不调用真实模型）：

- 分组：按发件人、域名合并，过滤垃圾邮件、忽略名单、少于 3 封的组；
- 推荐结果解析：未知的组 id 丢掉，重名、超长名称处理；
- 采用：标签创建、历史邮件打上、重名合并；忽略后下次推荐的提示词里带上它；
- 自动打标签：没有标签时提示词不变；输出里不认识的标签丢掉；手动去掉的不会被重新打上，手动加的不会被去掉；
- 搜索 `label:`、规则条件、删除标签后规则不再匹配；
- 开放接口和 MCP 返回标签，`PUT /messages/:id/labels` 需要 organize 权限。

前端在浏览器里走一遍：推荐、采用、侧栏、列表、详情加减标签、搜索。

1. 数据表 + 标签增删改 + 手动打标签 + 列表 / 详情 / 侧栏 / 搜索显示。

# 第二版：分类、标签、提示词都存数据库，支持多语言

状态：**已实现**。

## 起因

- 标签推荐只生成一种语言，切换界面语言后名称、说明不跟着变。
- 分类名称、分类说明、各功能的 AI 提示词散在代码和 i18n 文案里，界面上看不到。

## 原则

- **系统内置的只读**：10 个固定分类、所有系统提示词。可以查看，不能修改、删除。
- **AI 推荐的和自己加的可以改**：标签（名称、说明、颜色、是否在侧栏显示）可以编辑、删除。
- **每条都存多种语言**：按语言存一份 JSON，例如 `{"zh-CN": {...}, "en": {...}}`。以后加日语等不用改表结构。缺某种语言时，显示已有的那一份。
- **服务端两种语言都返回，前端按当前语言选**：切换语言立即生效，不用重新请求。

## 数据表

| 表 | 内容 | 能否修改 |
| --- | --- | --- |
| `categories`（新） | key（`finance` 等，邮件分析结果里存的还是它）、i18n（名称 + 给 AI 的判断说明）、颜色、排序 | 只读，`builtin = true` |
| `labels`（改） | `name` / `description` 换成 i18n；source：`suggested` / `manual` | 可编辑 |
| `label_suggestions`（改） | 名称、说明、理由都换成 i18n | 采用前可改名 |
| `prompts`（新） | key（如 `classify`、`labels.suggest`、`reply`、`translate.text`、`search.plan`、`report`、`assistant`）、用途说明、i18n 正文、可用变量（如 `{{days}}`） | 只读，`builtin = true` |

系统分类和系统提示词的默认内容仍写在代码里，**服务启动时同步进数据库**（以代码为准覆盖 builtin 行）。这样升级版本时提示词会跟着更新。读取一律走数据库（带内存缓存）；库里取不到时用代码默认值兜底，不会因为数据库内容缺失导致 AI 功能不可用。

0022 迁移还没上线，直接重写，不再追加新迁移。

## AI 怎么用

- **邮件分析**：分类列表和各分类的说明从 `categories` 取，标签列表和说明从 `labels` 取，都用系统语言（管理员界面语言）那一份。缺这种语言时用另一种。
- **标签推荐**：一次调用同时输出中英文两套名称、说明、理由。提示词按发起时的界面语言选；输出一律要两种语言。
- **其他功能**（起草回复、翻译、语义搜索、报告、助手、对话标题）：提示词改为从 `prompts` 取，按当前语言选，再替换变量。内容和现在的代码一致，只是挪了位置。

## 界面

**智能 → 分类与标签**（原「标签」页改名）
- 上方保留推荐区。
- 下方一张表，列出系统分类和我的标签。列：名称、说明、来源（系统 / AI 推荐 / 手动）、邮件数、侧栏显示、操作。
- 系统分类行带锁：没有编辑、删除；鼠标悬停名称可以看其他语言的名称。
- 编辑弹窗每种语言一个页签，各填名称和说明；至少一种语言有名称、一种语言有说明，没填的语言显示已填语言的内容。

**智能 → 提示词**（新页面）
- 表格列出所有系统提示词（名称、用途、说明、可用变量），点开在侧边抽屉里按语言查看全文，变量高亮。
- 只读，带「复制」。

## 用到分类、标签的地方

- 侧栏「分类」「标签」、列表和详情里的标签、规则条件、搜索 `category:` / `label:`、统计、日报周报、MCP 说明：名称都按当前语言显示。
- 搜索 `label:名称` 用任意一种语言的名称都能匹配。

## 不做

- 不允许修改或删除系统分类和系统提示词，也不支持自定义系统提示词。
- 分类仍然是一封邮件一个，标签可以多个。两者不合并。

## 实现顺序

1. 表结构和启动同步；分类、标签、推荐改成多语言；标签推荐输出两种语言。
2. 各功能的提示词改为从 `prompts` 读取。
3. 「分类与标签」页、「提示词」页；前端所有分类名称改为从接口取。
4. 测试：多语言回退、只读保护（没有修改接口，改系统提示词的请求返回 404）、启动同步覆盖、推荐输出两种语言、切换语言后显示对应语言。

## 实现说明

- 语言列表只有一处：服务端 `server/src/i18n/context.ts` 的 `LOCALES`，网页 `web/src/i18n/index.ts` 的 `LOCALE_CODES`。回退顺序：当前语言 → 英文 → 简体中文 → 任意一种（服务端 `pickLocale`，网页 `pickText`）。
- 加一种新语言：两处列表加上代码；`server/src/catalog/categories.ts`、`prompts.ts` 里每条补一份该语言的内容（测试会检查是否缺）；界面文案照常补。标签推荐的输出结构、提示词里的语言列表（用 `Intl.DisplayNames` 生成）、标签编辑弹窗的页签都按列表自动生成。
- 系统内容的代码位置：`server/src/catalog/`；同步和读取：`server/src/services/catalog.ts`（`syncBuiltins`、`prompt(key, vars)`、`categoryName`）。
- 标签名称不分语言、不分大小写全局唯一：任何一种语言的名称都不能和其他标签任何一种语言的名称相同。
- 接口：`GET /api/v1/categories`（系统分类）、`GET /api/admin/prompts`（系统提示词，只读）；标签相关接口的 `name` / `description` 是请求时界面语言的，另带 `names` / `i18n`（所有语言）。
